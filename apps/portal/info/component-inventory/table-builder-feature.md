# Table-builder feature (`apps/portal/src/features/table-builder/`)

Part of the component inventory (`INDEX.md`, beside this file, is the router).
Public surface only — the code is the source of truth; verify signatures before relying on them.


| Symbol | File | Purpose |
|---|---|---|
| `enqueueTableBuild(req)` | `tableBuild.service.ts` | One `apiRequest('tableBuild.create')`, minting the `requestId`. Partition keys go through `onTheWire`, which flattens the three-variant union the API's contract cannot express and **stringifies the projection bounds** — safe because the plane accepts numbers or strings and the DDL builder interpolates without arithmetic, asserted in `lambdas/api/test_enqueue_routes.py`. `ServiceResult<void>` (enqueued ≠ created), never throws. |
| `suggestTableName(folder)`, `isValidTableName(name)` | `tableBuild.service.ts` | Pure: sanitize a folder name to a catalog-safe suggestion / test a name against `CATALOG_IDENTIFIER_RE` (UX only — server re-validates) (SPEC-071). |
| `buildPartitionKeys`, `buildPartitionKey`, `validateDraftKey`, `emptyDraftKey`, `parseValues` | `partitionKeys.ts` | Pure draft→wire partition-key logic + per-row validation (name against `PARTITION_KEY_NAME_RE`, uniqueness, integer/date/string-enum config); empty list ⇒ valid flat `[]` (SPEC-071). |
| `CreateTableButton` | `CreateTableButton.tsx` | File-browser toolbar action → opens the dialog, enqueues for the active space, success/error `Toast` (SPEC-071). **The only create-table CONTROL — the sole caller of `enqueueTableBuild` — and it is mount-gated `!isMobile`.** Not the only way to create a table — there are three, and only this one is a control: `CREATE TABLE` typed into the Query editor runs through the same Athena path as a `SELECT` (`athena.service.ts` does not inspect the type), and the table-share plane issues its own `CREATE EXTERNAL TABLE IF NOT EXISTS` server-side. The editor is desktop-only for its own unrelated reason (`QueryMobileView` is browse-first with no editor), though a SAVED query holding DDL still runs from a phone. So building a table is deliberately desktop-only by two independent gates; the Explorer picker's folder step used to cover the phone and no longer exists. Help says so. Takes the browser's `selected` items and builds from the ONE folder in them — `createTableTarget` resolves the folder and the refusal together, refusing nothing-selected, several-selected, a file, and the space root. Eligibility is otherwise enforced server-side. |
| `createTableRefusal(prefix, rootPrefix)` | `createTableRefusal.ts` | The one pre-flight refusal on this control, on `writeLockRefusal`'s predicate-with-its-words precedent. A table's `LOCATION` is read recursively, so a build at the space root SUCCEEDS over `athenaresults/`, `saved_queries/`, `user_settings/`, `shared_files/`, `shared_tables/` and `archive/` — succeeding is what makes it worth blocking. Compares with `isAtRoot`, never a second `===`. The control plane raises `location_is_space_root` for the same case, on creates only (refusing a refresh would strand a root table already in a catalog). |
| `useCatalogCatchUp()` / `armCatalogCatchUp(db, table)` | `useCatalogCatchUp.ts` | `arm` after a successful enqueue; the hook re-reads that catalog on the next window focus. **The enqueue is not the event** — a build lands minutes later and announces itself in a notification, so without this a table dropped and rebuilt under the same name leaves the Data Explorer resolving to the pre-drop execution. **Module state, mounted once in `ProtectedLayout`**: the control that enqueues a build unmounts when the user leaves that route, so a per-component arm died with the control that set it — enqueue from Files, walk to the Explorer, nothing fires. It was written when there were two such controls and holds for the same reason with one. The table IS named (the plane creates exactly the name asked for or fails), which keeps the re-read from resetting every other exploration of the database. Residual: `focus` fires on blur→focus only, so a user who never leaves the window gets no catch-up until they do. |
| `CreateTableDialog` | `CreateTableDialog.tsx` | Name prompt (suggested + validated) + optional partition-keys section; Confirm gated on name **and** keys valid; inline submit-error banner (SPEC-071). |
| `PartitionKeysField` | `PartitionKeysField.tsx` | Controlled, ordered, reorderable/removable partition-key rows (name + type `<select>` + per-type projection config) with focus management + labelled dynamic rows (SPEC-071). Every error is on screen from the start, but announced (`Input`'s `announce`) only once its field is left — never on a row just added or a type just switched. |
| `TableBuildRequest`, `PartitionKey`, `DraftPartitionKey`, `PartitionKeyErrors`, `PartitionType`, `PartitionKeysResult` | `tableBuild.types.ts`, `partitionKeys.ts` | The request + wire partition-key shapes (match the SPEC-067 contract) + the editor's draft/error/result types (SPEC-071). |
| `enqueueTableRefresh(req)` | `tableBuild.service.ts` | The refresh half of the same queue (SPEC-145): `mode: 'refresh'` + `partitionKeys: []` (a refresh reconstructs the table's keys, never redeclares them) + `allowRemovals` **only when true** (SPEC-144 validates the flag, so absent ≠ false); `requestId` minted inside, sent through the API's `tableBuild.refresh` route, which stamps the caller and `mode`, and derives the FIFO keys. `ServiceResult<void>`, never throws. |
| `useTableRefresh(notify, linked?)` | `useTableRefresh.ts` | Dialog + enqueue state for Refresh table, shaped like `useTableShare`: `{target, busy, error, open, close, submit}`; `open(database, table, pending?)` takes the **`GlueTableSummary`** (the request's space comes from its `location`). `linked` is the derived notification-link target + the callback that retires it — the link-borne dialog is derived from the URL, never opened from an effect. Also owns the rail invalidation: once on submit, once on the next window focus, then disarmed (SPEC-145). |
| `RefreshTableDialog` | `RefreshTableDialog.tsx` | The refresh confirmation on `ConfirmDialog`: what a refresh does/doesn't do, the always-unchecked removals opt-in with its consequence copy, and — in the link-borne state — the named columns plus `confirmDisabled` until the box is ticked (SPEC-145). |
| `parseTableLocation(location)` | `tableRefresh.location.ts` | Pure: `s3://{bucket}/{prefix}` → `{bucket, prefix}` with a normalised trailing slash, `null` otherwise. The Query workspace's only route from a Glue table to its folder (SPEC-145). |
| `parseRefreshLink(search)`, `MAX_LINKED_COLUMNS` | `tableRefresh.link.ts` | Pure: parses `?refreshTable={db}.{table}&removed={names}` from the **raw** query string (never `URLSearchParams` — it decodes, and the names are percent-encoded around a comma separator). Identifiers validated against `CATALOG_IDENTIFIER_RE`, **column names deliberately not** (they are never catalog-safe); capped at 20 (SPEC-145). |
| `TableRefreshRequest`, `TableRefreshTarget`, `PendingRemoval` | `tableRefresh.types.ts` | The refresh request shape, the dialog's target (`pending` present ⇒ opened from a `columns_removed` link), and the parsed link. Never persisted (SPEC-145). |
| `TableBuildSpace`, `TableBuildMode` | `tableBuild.types.ts` | The space shape (extracted from `TableBuildRequest`, so a refresh caller can build one from a Glue table's location rather than the folder in view) and `'create' \| 'refresh'`. `TableBuildRequest.mode` is optional; absent ⇒ create (SPEC-143). **`enqueueTableBuild` does not forward it** — the body is built field by field, and SPEC-145 adds the refresh caller. |
