## Fences

- **A gate blocks on a NARROWED count, never a total.** Checkov enforces check IDs measured at
  **zero** — enforcing what passes rather than suppressing what does not — and the plan scan
  accepts by check ID **and** resource. **A line matching no finding is a hard error.**
- **A scanner's configuration is its COMMAND LINE, and what it DISCOVERS is refused.** Checkov
  reads a `.checkov.yml` from the `-d` directory, the working directory and `$HOME`; Semgrep skips
  whatever a `.semgrepignore` anywhere in the tree matches; gitleaks reads a `.gitleaks.toml` and a
  `.gitleaksignore` from the repository, and never sees a path a `-diff` attribute hides from `git
  log -p`; and all three read variables. Measured, each took a finding off a blocking gate while
  the job read as clean, from a file no reviewer reads as part of a gate. So every Checkov, Semgrep
  and gitleaks scan runs through its `*-scan.sh` wrapper, which asks the tool what decided the scan
  (`--show-config`, the report's skip reasons, gitleaks's debug log, `git check-attr`) and refuses
  anything but the command line and the defaults. A corpus plants each source against the
  installed version before the job's scans. Refuse, never ignore: an ignored suppression file reads
  as one. The empty root `.semgrepignore` only switches off Semgrep's built-in list, which skips
  every `test/` directory under the same reason. Still open: Checkov's flagless variables, and
  inline `nosemgrep` and `gitleaks:allow`.
- **"Did not run" is never "clean."** A broken scanner fails the job even in report mode, and
  `--quiet` must never come back: without `passed_checks` the gate cannot tell a pass from a check
  that never ran.
- **A new finding is scoped, not accepted.** Every shipped scanner failure carries a written
  disposition; the enforce list is regenerated by **any** spec adding a resource family.
- **A refusal is the half of the system no user exercises**, and a coverage number is blind to it:
  a `raise` is one line, so deleting its test barely moves the percentage while the happy path —
  which runs on every dev run and every real action — keeps the function covered. Assert the
  **reason code by name**, never that "something raised". The check is mechanical: enumerate the
  codes raised against the codes asserted. A review samples this; a sweep counts it.
- **Mutation-test the guard whose failure would be SILENT** — not every assertion. This project
  ships assertions that pass while the thing they name is false, so one targeted break-and-revert
  when the guard is written is worth it. A **sweep** of every guard afterwards is not: it costs a
  full suite run each and finds what writing the test carefully already would. The cheaper habit
  that catches the same class: assert the **reason** — the message, the named item — never just an
  exit code or a count, since the neighbouring path usually returns the same code.
- **Naming a test in a comment is a PROMISE, and the doc gate now holds you to it.** A comment
  saying some named guard reads this number is worse than a stale comment when the guard is gone:
  it talks the next reader out of the check they were about to make. Citations in `.py`, `.tf`,
  `.tftpl`, `.ts`, `.tsx` and `.md` are resolved against the suite — in backticks, as a filename,
  or BARE inside a comment, the form a backticks-only reader cannot see and the one 11 of this
  repo's citations use. Specs, delivery docs and test modules are **not** judged, for reasons the
  checker states; a citation there is on you. Two consequences that apply green and fail
  later. **Deleting
  a test silently breaks every doc that cites it**, so the sweep for its name comes before the
  deletion, not after CI. And **a past-tense record of a retirement must contain the word
  "retired"** within a hundred characters of the name — that is the whole exemption, deliberately
  not "deleted" or "removed", which this repo uses constantly in live claims about deletion
  semantics. A record worded any other way reddens a ratchet whose end state is zero, and the
  answer is to reword the sentence rather than to raise the number.
- **`ACCEPTED_` tripwires record what has NOT been verified**: pin today's behaviour, name the
  reasoning, and say *revisit the decision, don't delete the test*.
- **No silent caps.** If a check bounds coverage, say what was dropped — silent truncation reads as
  "covered everything".
- **A gate's POPULATION is a claim, and an EXEMPTION is a hole shaped like one.** Two wildcard rules
  read 2 of 17 IAM documents and passed on the 2 they read. Counting the population against the
  directory it came from catches an ADDITION and nothing else — both sides shrink together on a
  deletion, so only a comparison against an **independent** source sees that. And an exemption
  carved for a real case must name the ITEM it excuses, never the container: "a conditioned
  wildcard is narrowed" admitted an account-wide `iam:PassRole` behind `aws:RequestedRegion`,
  where "this ACTION is narrowed by this measured key" costs nothing and admits none. All three
  were found by planting, not by reading.
- Coverage floors and `"strict": true` are **declared, never inherited**. The floors are a flat
  **85**, no longer ratchets at the measured level — a ratchet fails CI on any deliberate reduction
  in test volume, and is bought back by testing internals. Never lower one for a regression, and
  never read a floor as evidence a guard exists: four mutations of production code once passed the
  whole suite with coverage unchanged. **Mutate the guard instead.**
- **A rule that prose asks every session to remember is a rule nothing enforces.** The queue told
  sessions to rebase after the wait for as long as it existed, and the hook checked only the lock;
  it now refuses a push whose commits do not contain the remote's trunk. When a document says
  "always X before pushing", ask what refuses the push without X — and if the answer is a
  paragraph, write the check.
- **A script a test EXECUTES must keep its scratch files private.** A workflow step naming a fixed
  path under `/tmp` is one file per *job* on a runner, and one file per *machine* under the suite —
  which runs those scripts verbatim, on a checkout several sessions work at once. Two runs truncate
  and rewrite it: the loud half is a `jq` parse error on spliced bytes, the quiet half is a clean
  read of the OTHER run's fixture, which answered a wrong verdict with no error and passed as a
  flake on a different test each time. Create the file with `mktemp`; `$RUNNER_TEMP` is for one
  that must cross steps.

## Security scanning (SPEC-138)

Five classes of scan across all three surfaces — SAST (Semgrep `p/owasp-top-ten` + language rulesets), dependencies (`npm audit` at **two scopes**, `pip-audit` over glob-discovered requirements), secrets (`gitleaks`, full history, redacted), IaC (`checkov` on `infra/`) and DAST (OWASP ZAP baseline, weekly, unauthenticated). Three decisions carry the weight. **(1) Gating is data, not code:** one `GATE_*` value per scanner in `security.yml`, all `report` at ship, and an unrecognised value is a *hard error* — a typo must never silently mean "not enforcing". The exception is `eslint-plugin-security` + `no-unsanitized`, which run inside `npm run lint` (now `--max-warnings 0`): an injection sink in code being written now should stop the PR, not become a line in a report. **That guarantee no longer rests on CI.** `ci.yml`'s `Lint` step is disabled to save Actions minutes, so unlike the four scanners above — which GitHub enforces regardless of what any session does — this one is enforced by the mandatory pre-push run alone, and a session that skips it puts a sink on `main` behind a green PR. **(2) Every scanner is version-pinned**, for the reason `pyproject.toml` already records — ruff 0.16.0 widened its defaults and reddened `main` with 500 findings in untouched files (#311); a scanner that gains rules on release does that to every open PR at once. **(3) "Did not run" is never "clean":** unparseable output, a scanner exit ≥ 2, or Checkov `parsing_errors > 0` fails the job *even under `gate=report`*, and Semgrep's partial-parse count is published beside its finding count. That is SPEC-137's failure mode — three gates all satisfied by an import that could never resolve — and a zero from a broken scanner reads as evidence, which is worse than no scanner. **Not available, not declined:** CodeQL, SARIF upload and the Security tab need GitHub Code Security, which a private repo on a personal account does not have — hence the job-summary-plus-artifact substitute and the fact that each run is a fresh snapshot with no cross-run deduplication. **Declined on merit:** OWASP Dependency-Check (NVD-centric, slower and less accurate than the ecosystem-native audits) and a second `bandit` (ruff already selects `S`). **Known blind spot:** Checkov parses `.tf`, so the `.tftpl` IAM policies that implement the whole `${aws:PrincipalTag/username}` isolation model are opaque strings to it — a green Checkov job says nothing about the authorization model, and closing that needs `checkov -f plan.json` against a `tofu plan`. First-run findings and their dispositions: `docs/security-baseline.md`.

## IAM policy scanning = the rendered plan, not the templates (SPEC-139)

SPEC-138's Checkov step reads `.tf` and therefore evaluates **zero** IAM policy-document checks, because every policy in this system is a `templatefile()` call it cannot resolve. `deploy-infra.yml`'s plan job now saves the plan, renders it with `tofu show -json`, and scans that with `--framework terraform_plan`: **431 IAM checks against 55 IAM resources**, where the `.tf` scan evaluates none. It lives in `deploy-infra.yml` rather than `security.yml` because the plan and the AWS credentials already are, and that workflow is now in **its own path filter** — otherwise a change to how we scan the infrastructure could merge having never run. **Renaming the `.tftpl` policies to `.json` was raised and REJECTED on measurement:** Checkov emits nothing — zero findings, exit 0 — for a standalone policy file containing `"Action": "*", "Resource": "*"`, because it evaluates `aws_iam_policy` *resources*, not loose documents. The extension was never the blocker; the unevaluated `templatefile()` in the `.tf` was. Keeping `.tftpl` also keeps the signal that `$${aws:PrincipalTag/username}` escaping applies, which is the most error-prone thing about these files. (51 of the 57 templates happen to parse as JSON; 6 do not.) **Two scanners, deliberately:** the `.tf` scan runs every PR + weekly and reports checks the plan scan does not; the plan scan is the only one that reads IAM. Neither is redundant. **The scan asserts its own coverage:** if the plan holds `aws_iam_policy` resources but no IAM check was evaluated, the job fails — a silent regression to the `.tf`-only state would otherwise look identical to a clean run, and that tripwire caught a real matcher bug (`^aws_iam_` never matches `module.data.aws_iam_policy.x`) before CI did. First-run result: the isolation policies are **clean**; all 6 IAM findings are deploy-role `lambda:*EventSourceMapping` statements on `Resource: "*"`, an action AWS does not allow to be resource-scoped — the available hardening is a `lambda:FunctionArn` condition key. Detail: `docs/security-baseline.md`.

## A scanner gate blocks on a narrowed count, never a total (2026-08-09, completes SPEC-138)

SPEC-138 shipped every scanner as `report` and `docs/security-baseline.md` proposed a threshold for
each. Four now block: `gitleaks` and `pip-audit` at a true zero (2026-08-02), and **Semgrep** and
**Checkov** here, plus `GATE_CHECKOV_PLAN` on the rendered-plan IAM scan. Semgrep needed one thing —
`--exclude-rule` for a Flask template-injection rule in a fleet with no Flask, excluded **by rule ID**
rather than by dropping `p/owasp-top-ten`, with `test_semgrep_excludes_exactly_the_flask_rule`
asserting it is the only `--exclude-rule` in any workflow, so a second cannot arrive without an
edit to that test, whose failure asks for the disposition. Checkov needed a shape.

**The shape is an ENFORCE list, not a suppression list.** Checkov reports 373 failures over 22 rules
on `infra/`, nearly all of them documented accepts — no VPC, no CMK, no X-Ray, no WAF. Gating that
total would mean suppressing 22 rules to enforce a handful, producing a file nobody reads and a gate
whose meaning drifts every time the scanner adds a rule. So `.github/checkov-enforced.txt` names the
**52 check IDs measured at zero**, and the gate counts failures on those; the rest publish and do not
block. **The criterion is "passes today", not "matters most"** — two entries are merely operational
(`CKV_AWS_216`, `CKV_AWS_305`) and are in because they pass. Deciding which checks *deserve*
enforcement is an argument to re-litigate on every infra change; holding everything already clean is
not, and it costs no remediation to turn on. Same ratchet-at-the-measured-level shape as the coverage
floors (SPEC-150) and the mypy baseline.

**The plan scan accepts by check ID AND resource, never by ID.** Its two permanent findings —
`CKV_AWS_290`/`CKV_AWS_355` on `module.base.aws_iam_role_policy.github_actions_deploy` — exist because
the deploy role must create resources that have no ARN yet and no applicable condition key. Keyed by
resource, the same two rules firing on any other policy still fail; keyed by ID alone, the exemption
would silently cover the isolation policies, which is the one thing this scan exists to watch.

**Three implementation facts that are not obvious and will bite again:**

- **`--quiet` strips `passed_checks`**, and without them an enforced ID that passed is
  indistinguishable from one that never ran. The flag is gone from the `.tf` scan (the plan scan had
  already learned this) and a test pins its absence.
- **An enforced ID evaluated against nothing is a hard error, not a pass** — and so is a plan-scan
  acceptance that matches no finding. A typo, a rename in a scanner bump, or a resource class
  leaving the repo all yield a line that enforces nothing while reading as enforcement: "did not run
  is never clean", turned on the gate's own configuration. **Neither Checkov gate can redden a
  production deploy:** `deploy-infra.yml`'s `plan` job is `pull_request`-only and `apply` does not
  depend on it, so both gates block PRs and nothing else.
- **A gate's count defaults to a NON-NUMERIC sentinel, and its narrowing step assigns before it
  echoes.** These two together are what make the hard errors above reachable, and the first draft
  had neither — every one of them arrived at the gate as a silent green. `echo "VAR=$(script)"` does
  **not** fail the step when the script fails: `echo` exits 0, `set -e` sees success, and the empty
  value it writes wins over any earlier record. Only an assignment's failed substitution trips
  `set -e`. And `${VAR:-0}` substitutes on **empty** as well as unset, so a numeric default converts
  "no count was written" into "clean" — `apply-gate.sh` rejects a non-numeric count, which is what an
  absent count is. ZAP's pre-existing `no-report` default is the same idea; it was there to be copied
  and wasn't. **A pessimistic pre-write does not substitute for either**, which is what the first
  draft believed. **A count that several steps write needs every step after the first to write
  the sentinel before it narrows**, because the default only covers a count that nothing wrote, and
  a step that hard-errors writes nothing. When the Dockerfile narrowing failed after the terraform
  narrowing had written a zero, that zero stood as the total, and the gate printed "no findings"
  over a red step. The summary's full count, written before the terraform narrowing, stood in the
  same way when that narrowing failed, so `security.yml` no longer writes it. The Dockerfile step
  now writes `no-count` first, and refuses to add a terraform count that is not a number, because
  bash arithmetic reads an empty value or `no-count` as zero.
  `test_the_checkov_gate_counts_both_frameworks_or_refuses` replays the steps that touch the count
  the way the runner does, and refuses to run unless they are every step that names it.

**One exposure accepted, and it is not the Checkov one.** Semgrep's binary is pinned but its
`--config p/*` rulesets are fetched from the registry at scan time and are **not** — so an upstream
rule addition can redden every PR with no code change, the shape #311 made this repo pin everything
to avoid. Accepted because `pip-audit` already blocks on a live advisory database with exactly the
same property, and because the alternative (vendoring 157 rules) trades a rare interruption for a
permanent staleness. The Flask false positive is the demonstration that these rulesets misfire here;
if a second arrives, the answer is another `--exclude-rule` with a disposition, not a narrowed count.

**Still not blocking, by decision:** `npm audit` — `apply-gate.sh` has no severity threshold and the
runtime scope still carries accepted `dompurify` advisories (monaco vendors its own copy), so a
flip would redden every PR; ZAP — two Lows survive by decision, so gate by `riskcode >= 2` or not at
all. Record: `docs/security-baseline.md` → *Addendum — The Gates Went On*.

## Compiler and coverage defaults are declared, never inherited (SPEC-150)

`tsconfig.app.json` and `tsconfig.node.json` state `"strict": true` even though TypeScript 6 already
defaults it on, and both suites carry **literal** coverage floors. Adding the `strict` key changed
**zero** errors — that is the point, and a build that finds otherwise should stop and re-derive the
premise rather than "fix" the errors.

This reverses the implicit trade-off of leaving a default alone because it happens to be correct.
`pyproject.toml`'s ruff block is the precedent and says it outright — "THE RULE SET IS CHOSEN HERE,
NOT INHERITED" — after ruff 0.16 widened its own default set from 59 rules to 413 overnight and
turned `main` red with 500 findings in files nobody had touched (#311). A default is a decision
*someone else* gets to change; strict is this project's single most important type guarantee, and it
does not ride on one.

The coverage floors are the same principle pointed at a different kind of erosion: both suites
measured coverage and neither gated on it, so deleting tests passed CI identically to keeping them.
They are hard-coded literals on purpose. Nothing computes, inherits or reads them from a file, so
changing one is a visible one-line diff in review rather than a number that drifted.

> **Superseded — the ratchet is gone; the floor is flat 85.** They were ratchets at the measured
> level (portal 91/86/89/93, lambdas 95) until the suites were rewritten around entry points rather
> than around individual functions. A ratchet at the measured level makes any deliberate reduction
> in test volume fail CI, which is the opposite of what was wanted, and it rewards adding tests
> around internals to buy back a tenth of a point. Both suites now sit at a flat **85** and stay
> there: raise it only with a reason that is not "coverage happens to be higher today", and never
> lower it to accommodate a regression.
>
> **What that costs, measured.** A coverage floor was never a measure of guard strength, and the
> review of that rewrite proved it: four separate mutations of production code — an archive
> rollback default that routed to deletion, a route minting its own AWS client, the CI watcher
> reporting a red run green, and a verb losing its `@traced` — each passed the full suite with
> total coverage unchanged to the hundredth of a point. **Mutate the guard; do not ask coverage
> whether it exists.**

**Do NOT read this as "enable strict"** — it was already on. The work is *declaring* an inherited
default, which is a much smaller and different thing.

**The typecheck gate itself is separate and already shipped** (#363): `ci.yml` runs `npm run build`
on every PR. Two traps are recorded in that file's header comment and should be read before touching
it — vitest does not typecheck, and `tsc --noEmit -p apps/portal/tsconfig.json` **exits 0 having
checked nothing**, because that config is solution-style (project references only, no
`files`/`include`). `tsc -b` is the only invocation covering the app *and* its `*.test.tsx` files.
SPEC-150 confirmed the gate empirically on a scratch PR: with the #361 defect reintroduced, Lint and
Format check passed, **Build failed**, and Test was skipped.

## `ACCEPTED_` tripwires: what the project knows it has not verified (SPEC-153)

The repo invented this idiom in SPEC-110 (`test_ACCEPTED_the_span_error_stack_may_carry_file_contents`).
SPEC-153 makes it the standard way to record a **load-bearing premise that is corroborated but not
discharged**, and a **documented behaviour someone will later mistake for a bug**.

A tripwire test pins **today's behaviour**, names the reasoning in its docstring, and ends with the
same instruction every time: **if it starts failing, revisit the decision — do not delete the test.**
That is the whole point. A premise held only in prose degrades silently; a premise held in an
assertion tells you the day it stops being true.

Four now exist. Two pin premises:

- **Athena's column-name fold** (`test_apply_refresh.py`). AWS documents that Athena lowercases every
  column name it creates through DDL, which is why SPEC-149 hard-codes the fold — but 149's in-place
  `UpdateTable` bypasses Athena, so the fold is now **ours**. If the premise is wrong, the first
  refresh of a mixed-case table silently re-cases every column while `diff-schema`, which folds case
  to compare, reports them unchanged: a mutation no test and no notification would report. The
  tripwire pins that a live `Order_ID` becomes `order_id` and the carried comment survives. Still
  **corroborated, not discharged** — the `GetTable` read-back that would discharge it is an owed live
  check.
- **The projection round-trip** (`test_load_table_definition.py`). The existing round-trip builds its
  fixture from `ddl.projection_properties` and compares the reconstruction re-rendered through the
  same function: render → parse → render vs render. It proves the parser is a left inverse of the
  renderer **on the renderer's own image**, which is worth having and is not "reads tables this
  pipeline did not write". It was **kept and renamed to say so**, and a second fixture whose
  properties did not come from our renderer was added beside it, with a guard test that fails if the
  fixture ever becomes the renderer's output.

Two pin accepted behaviour:

- **A redelivered notification create writes a second inbox row** (`test_notifications_writer.py`).
  These pipelines are at-least-once and `apply_create` mints a fresh `uuid4` per invocation; FIFO's
  producer-side dedup window does not bound a visibility-timeout redelivery. **Accepted:** the blast
  radius is one duplicated line in a read-only, dismissible list, while the fix with teeth is a
  producer-supplied idempotency key — a contract change across four control planes and the browser
  producer. `dqcommon.index_store` handles the equivalent case by replacing the row, and the
  asymmetry is now stated rather than accidental.
- **The runs-index cap evicts by position, not by timestamp** (`test_index_store_dqcommon.py`). Once
  a replay has moved a row to the end, position order and timestamp order disagree and the next new
  run drops a row that is newer in time. **Accepted:** the code says at the cap that the dashboard
  sorts by timestamp itself, and every evicted run's report object is untouched.

A tripwire is **not** a licence to leave a defect. It is the difference between a project that knows
what it has not verified and one that has forgotten.


## A refusal is the half of the system no user exercises (2026-08-28)

A control-plane verb is mostly its checks, and each one is a `raise TerminalError("<reason>", …)`
whose first argument is a closed vocabulary driving the user-facing wording. **That reason code is
the thing a test must assert by name** — "something raised" passes against the neighbouring path,
and against an `ImportError` at cold start.

**Refusals are the half of the system nothing else exercises.** The happy path is self-policing: it
runs on every dev run, every live check and every real user action, so it fails loudly and
immediately. A refusal path runs only when something is already wrong. When one stops working the
system does not error — it **proceeds**, does the thing the check existed to prevent, and reports
success.

**A coverage number is close to blind to them, and a coverage-driven cleanup eats them first.** A
`raise` is one line; delete the test that drives it and the surrounding function is still executed
by the happy-path test, so the percentage barely moves. Measured on the suite reduction that
produced this entry: reason codes with a test asserting them fell **62 → 34 of 85** while total
coverage stayed above its floor throughout.

**The check is mechanical, so run it rather than reviewing for it.** Enumerate the reason codes
raised across `lambdas/`, enumerate the ones a test compares against, and diff. It answers in
seconds and returns the whole population. Three fresh-context review frames over the same change
returned 4, then 7, then 17 findings — diverging, because a review samples where an enumeration
counts.

> The 28 codes this project knowingly stopped asserting are listed on the PR that reduced the
> suites. Restoring one is `git show <ref>:<path>` plus a prune; the decision to leave them was
> deliberate, not an oversight.

## An axe rule that cannot measure is disabled, and what replaces it (2026-09-01)

`src/test/axe.ts` ran axe under the `wcag22aa` tag, which includes **`target-size`** — WCAG 2.2
SC 2.5.8's 24×24 CSS px floor. jsdom has no layout engine, so every `getBoundingClientRect` is
0×0, and the rule does **not** error on that the way `color-contrast` does. It reports a **PASS**,
worded *"Safe clickable space has a diameter of 24px which is at least 24px"*, for two adjacent
10×10 buttons. Measured, and pinned as a tripwire in `src/lib/targetSize.test.ts` so the day jsdom
gains layout the rule can be turned back on.

**The hazard is the rule's presence, not its absence.** A reviewer asking "do we assert target
size?" got yes, and axe's own output recorded a pass — the same shape as the dark-mode contrast
blind spot, and the reason the fix is a disable *with a reason* rather than a note somewhere. The
disabled set is now one exported constant spread into all three options bags, asserted as such,
because a bag that spells its own `rules` map and forgets an entry is invisible.

**Audited the rest.** The base bag's tags select **70 rules** (route specs add `best-practice` for
100; a sample of those was probed too and turned up no second offender, but they were not swept); each one that plausibly needs layout, computed
style or a document was probed with markup built to violate it, and the rest were read off as
DOM-only. Four come back silently **inapplicable** rather than passing —
`scrollable-region-focusable` (nothing in jsdom reports as scrollable), `link-in-text-block`,
`css-orientation-lock`, `no-autoplay-audio`. Two come back **incomplete**, which
`toHaveNoViolations` ignores outright — `aria-hidden-focus`, `avoid-inline-spacing`. Two more
(`meta-viewport`, `bypass`) find nothing because the assertions are handed a container rather than
a document. **`target-size` is the only rule measured reporting a pass it cannot make**, which is
what separates it from all of those: an inapplicable rule records nothing and misleads nobody.
`p-as-heading` was suspected on the same grounds and cleared — it violates correctly, on a fixture
built for it, so the suspicion was wrong and the rule stays on.

**What replaces it, and what deliberately does not.** `src/lib/targetSize.test.ts` sweeps every
`.tsx` for interactive tags whose own `h-*`/`w-*`/`size-*` classes fall under the floor, with the
threshold **computed** from Tailwind's `--spacing` and the app's 14px root rather than written
down — one step is 3.5px, so `h-6` is 21px and `h-7` clears by half a pixel. Three limits, all
stated in the file so its silence is not read as coverage:

- **Under 24px is a candidate, not a violation.** SC 2.5.8's spacing exception exempts a small
  target nothing else comes within a 24px circle of. That is geometry the suite cannot do, so the
  register is named `ACCEPTED_UNDERSIZED` and its notes say what a control *is*, never that it
  conforms. A sweep reporting every small control as a violation would manufacture failures on
  correct code — the same defect as the axe rule, pointing the other way.
- **A control whose height comes from its TEXT is invisible to it, on purpose** — and the full list
  of limits lives at the top of the test file, not here, so the two cannot drift. The distinction
  worth keeping in the register is the one that decides whether a static check is honest: a bare
  `text-sm` link is ~15.5px and a `px-3 py-2 text-sm` menu row is 32px, so demanding a height class
  from either would fire on the correct one; but a **checkbox or radio is a replaced element**, with
  no line box padding can grow, so an unsized one is the UA's 13×13 box and there is no correct
  variant to false-positive on. The general argument does not transfer, and reading it as though it
  did left the app's largest population of small controls unexamined until a review counted them.
- **A guard against this class of defect must be planted against.** Every assertion here was
  broken deliberately and watched go red before being reverted, because a check for a vacuous
  guard that is itself vacuous is worse than none. Planting found three holes that reasoning had
  not: an apostrophe in a source comment (`SC 2.5.8's`) read as an opening quote to the attribute
  scanner and hid one control entirely; taking the **first** `className` on a tag read a
  decorative icon's size as the control's whenever JSX attribute order put the icon prop first
  (depth, not position, is what distinguishes them); and the register, keyed by FILE, exempted
  twelve whole files — a registered control could shrink from 21px to 7px, or be half-fixed,
  with nothing going red. It is keyed by the **measured offences** now, so a change to any of
  them is a change to the list.

  Two more were self-referential, and both are the same mistake: an assertion that derives its
  expectations from the thing it guards cannot see that thing shrink. The loop checking the
  disabled rules iterated the constant's own keys, so DELETING `target-size` — restoring the
  vacuous rule across all 41 axe specs — shrank the loop and passed. The set is spelled out now.

**Encode an absolute threshold in an absolute unit.** `min-h-[24px]` is 24px under any root;
`min-h-7` is 24.5px under this one and 21px under a 12px one, and nothing would catch the change.
A rem step expresses visual rhythm, and rhythm is not what this value is for.

## A change-detection gate answers three ways, and one of them is not an answer (2026-09-04)

Two workflows skip expensive steps when a change set touches nothing they read: `ci.yml`'s scope
step, which gates the install, the build and the bundle check on a pull request, and
`deploy-spa-image.yml`'s, which gates the image build. Both decide by matching `git`'s path list
against an anchored pattern list. Every way that decision can go wrong answers "nothing changed"
— the **cheap** direction, behind a green check, with the same reassuring annotation an honest
skip prints. `ci.yml` had two such ways and has been fixed; `deploy-spa-image.yml` was written
with both guards already in it and never had either, so this entry is about the class rather than
about a defect the two shared.

**Read paths RAW.** `git diff --name-only` (and `ls-files`, and `ls-tree --name-only`) C-quotes any
path that is not plain ASCII: `apps/portal/src/café.tsx` comes back as
`"apps/portal/src/caf\303\251.tsx"`, wrapped in double quotes with the bytes escaped, which matches
`^apps/portal/` and every other anchored pattern. **`core.quotePath=false` is not the fix** — it
covers bytes >= 0x80 alone and leaves `"`, `\` and control characters still quoted, so it closes one
member of the class. `-z` plus `tr '\0' '\n'` closes the class. The residual is a newline inside a
filename, which splits one path into two: for a prefix anchor both halves are tested and it
over-selects, in the expensive direction; for a `$`-anchored pattern with a wildcard segment —
`^infra/modules/[^/]+/policies/[^/]+\.json\.tftpl$` is the only one — neither half matches and the
path is lost in the cheap one. Measured and accepted: closing it means abandoning line-oriented
matching for a filename nobody writes. The same defect was found and fixed in two IAM guards
reading `ls-files` and `ls-tree`, where it dropped a template out of a guarded population.

**Guard a broken pattern list with a POSITIVE CONTROL, not an enumeration of failure modes.**
This was learned by getting it wrong. `grep` answers three ways and only two are answers — 0
matched, 1 did not, anything above is grep failing to perform the test at all — so a bare `if`
collapses the third into the second and an unusable list reads as "nothing changed". It is
**self-concealing** in `ci.yml`, because the workflow is in its own pattern list: the pull request
that breaks it skips its own build, merges green, and every later one skips too.

Reading the status and hard-erroring above 1 was the first fix, and it covers **one** shape.
Measured on GNU grep 3.11, the runner's engine: an unbalanced bracket exits 2, but a non-capturing
group, a lookaround and a stray `\d` all exit **1** — an ordinary "no match" — and two of the three
are not diagnosed at all. An empty list is a fourth. So the step now runs a path the list must
always select through the same invocation and refuses anything but a match. That covers empty,
uncompilable, silently reinterpreted, and edited-until-it-no-longer-selects-the-app, including
shapes nobody has enumerated. The status check stays as the narrower diagnostic — with the canary
matched, a failure above 1 is grep failing on the *change set*, which wants a different message.

Do **not** reach for the static sanity tests instead: they run only in a session's local pytest.
And note which way that asymmetry runs, because the intuitive version of it is backwards — Python's
`re` **rejects** the unbalanced bracket the step now catches on its own, and **accepts** the `(?:`
and `(?=` it does not.

**The step's own claim to fail expensively is now load-bearing on `pipefail`.** As a simple
assignment, a failing `git diff` killed the job under `set -e` alone. As a pipeline, the status is
`tr`'s, and `tr` succeeds over nothing — so without `pipefail` every pull request answers
`app=false`, silently. Asserted both ways: the flag is read out of the step, and a diff that cannot
be computed is exercised.

**A skip prints the change set it decided over.** A verdict with no evidence under it makes a wrong
`app=false` undiagnosable from the log — the notice alone cannot distinguish an honest skip from a
pattern list that has stopped covering an input.

**What the guards over this owe, beyond the verdicts.** `lambdas/test_ci_scope.py` runs both steps'
real scripts, taken from the workflow rather than restated, against throwaway repositories. Two
controls make the rest worth anything. On the **answer** side: a harness that answered `app=true`
unconditionally would satisfy every quoted-path case while proving nothing, and the step takes
exactly that branch by design when the base is unreachable — so a documentation-only commit must
still skip and neither verdict may reach that escape. On the **input** side: for any fixture path
that is not plain ASCII, the un-`-z`'d diff must still be shown to quote it, or the fixture has
stopped provoking the hazard and the guard over it is vacuous. That one is reachable without a code
edit — a developer with `core.quotePath=false` in their own git config — which is why the harnesses
scrub git's configuration out of the environment. Pointing `GIT_CONFIG_GLOBAL` and
`GIT_CONFIG_SYSTEM` at `/dev/null` is **not** sufficient on its own: `GIT_CONFIG_COUNT` with its
numbered key/value pairs, and `GIT_CONFIG_PARAMETERS`, set the same option with no file involved,
so all of them go. `GIT_DIR` goes with them for a different and worse reason — inheriting it does
not merely break hermeticity, the fixture commits land in **that** repository. Measured before the scrub: a decoy
repo came back with its `HEAD` moved onto a fixture commit and its original orphaned, while the
suite passed green.

`TMPDIR` joins that list, and it is the costliest entry on it. These scripts do not only read the
environment, they CREATE files — and a name fixed in the script is one file shared by every run of
the suite on the machine, which several sessions of this project run at once as their pre-push
gate. Two runs truncate and rewrite it. The loud half is a `jq` parse error on spliced bytes; the
quiet half is a clean read of the other run's fixture, which took the no-baseline branch and
answered *build and deploy* — a wrong verdict, reached with no error, by the step whose only job is
that decision. Reproduced in three concurrent runs of the file; it had been failing about one full
suite in six, on a different test name each time. The loud half has NO fixed signature, which is
the trap for anyone tempted to assert on it: whichever run writes second owns the front of the
file, so a longer write over a shorter one leaves a head (`Invalid numeric literal at line 2,
column 12`) and a shorter over a longer leaves a tail (`Unmatched ']' at line 2, column 1`). Both
were observed, on two machines. A guard here asserts that the step FAILED, never what it said. So the workflow creates its scratch files with
`mktemp`, the harnesses point `TMPDIR` at the throwaway directory they already clean up, a sweep
refuses a fixed path under a shared temp root in everything the suite executes, and a concurrency
case asserts what the sweep cannot spell — two fixtures whose verdicts contradict, so a collision
cannot be absorbed as a coincidence. Left deliberately: `spa-image-matrix.sh` keeps a dozen fixed
`/tmp/matrix-*` names, which are the same defect on the HOST and would corrupt two concurrent runs
of it. No test executes that script, so it cannot flake this gate; fixing it is its own change.

## A parity fixture becomes a floor once the cutover it guarded is closed (2026-09-05)

The container cutover froze a capture of every Lambda's settings and held the planned fleet
**equal** to it in both directions — the right shape while 86 functions were being replaced and
nothing else was allowed to move. The cutover closed, the fixture stayed frozen (regenerating it
would make it agree with whatever the code says), and the first plane added afterwards was refused
locally, before any PR existed, by the offline test that holds the capture equal to `fleet.py`'s
derivation — and `lambda_plan_guard.py` in `deploy-infra.yml`'s plan job would have refused it the
same way, since its equality loop had no other branch: a function the fixture never saw, and a
queue URL added to the API's environment, both read as drift. No PR between the cutover and that
plane had added a function or an environment variable, so a gate that ran on every infra PR had
never been exercised on the case it now refused.

**The guard is a floor.** Every captured function must still exist with every captured field
intact, and every captured environment variable must still be set to its captured value; a
function the fixture never captured is an addition, named on stderr and accepted, and a variable it
never captured is allowed. The offline test names the additions explicitly
(`ADDED_SINCE_THE_CUTOVER`), so an accidental function still fails by name rather than shrinking
into a tolerated difference. Each edge of the floor was mutation-tested: refusing an addition,
ignoring a vanished function, ignoring a removed or changed variable, and refusing an added
variable each reddened exactly one test. Not retired: the floor still holds what the cutover
promised, and the packaging, population and permission-by-ARN checks beside it are untouched.

**The floor was half the answer, and CI found the rest one refusal at a time.** Three more things
in the same machinery refused a plane that had done nothing wrong, and none was reachable until
one was added — so each arrived on its own CI run, after the local gates were green.

- The **extractor** — a step whose own comment says it is not the gate — ran `capture` under
  `set -e` on every plan, and `capture` correctly refuses a plan carrying an unknown value. A
  plan that creates a queue always carries one. It now says why it could not extract and
  continues.
- The **unknown-parity-field refusal** demanded the attribute be "declared explicitly", which is
  a remedy that exists for a memory tier and not for a role ARN belonging to a role created in
  the same plan. It now applies in full to the functions the fixture CAPTURED, where a skipped
  comparison is the promise going quiet, and to an ADDITION only for the three fields
  `docker-lambda` sets as literals. Both directions mutation-tested.
- The **`environment` leg is RETIRED**, not patched again. Two attempts to keep it — a
  per-variable floor, then a reader for all four shapes Terraform marks an unknown with — each
  passed locally and each was refused by the next real plan, the second one crashing on a shape
  its hand-built fixture did not have. What finally settled it was reading what the leg
  PROMISED: "the cutover changed no function's environment" is a claim about one apply, and held
  as an eternal floor it refuses a plane joining the DLQ drain's list, which is a change the
  plane exists to make. It is retired with its replacement named, per the fence — 
  `test_fleet_environment.py` derives every variable each function's code can reach and asserts
  its environment supplies it, which is both stronger and live where the fixture is frozen.

The lesson is about gates rather than about this gate: **a check written for a one-time event
keeps running afterwards**, and its preconditions quietly become claims about every future
change. Every refusal here was right for the cutover and wrong for the first ordinary growth
after it, and none could be observed until something grew. The second lesson is the cost of
patching instead of reading: two rounds went into keeping a comparison whose promise had already
been kept, and the question that ended it — *what did this leg actually promise, and is that
still a thing that can be true?* — was available at the start.

## A citation is a promise, and the ratchet is exact in both directions (2026-09-08)

Comments and docs across this repo name a test as the thing enforcing a claim beside them. One
commit deleted 57 files, 53 of them test modules, and nothing swept the references: 46 such
citations were left standing, seven of them in `locals.tf` comments asserting that a named test
reads a cap back and would fail the build if it were raised. No such test existed. That is worse
than a stale comment, because it discourages precisely the check a careful reader was about to
make.

`check_test_citations` resolves every citation it judges against the suite, in three grammars. The
bare-in-a-comment form is the one that matters: it carries 11 of the 255 judged sites and every
Terraform citation this work existed to repair, and a backticks-only reader sees none of them.

**The ratchet is EXACT, not a ceiling, and that is the load-bearing choice.** A ceiling can only
see the count rise. Measured on this gate, adding one filename to the excluded set dropped eight
findings and stayed green; widening the retirement window to the whole file dropped seventeen. Both
are lost detection, and lost detection is invisible to a ceiling forever. With an exact ratchet a
fall is also an error, which forces the author to look at what stopped being reported and say so by
moving the number. The cost is real — an unrelated PR that deletes a file carrying a stale citation
must lower the constant — and it is the price of the gate being able to see its own blind spot.

## The queue reads `main`'s build from its push runs, and nothing else that records its sha (2026-09-10)

**What happened.** After a merge, Dependabot's security-update job ran against `main`'s head, and
failed: the update was not possible, because another package pinned the vulnerable version. Every
deploy of that head was green. The queue's `main-green` counted every Actions run on the head sha,
so it answered `main IS RED` to every session — and the only thing that moves the head is a merge,
which the queue refuses while `main` is red. No re-run could succeed while the conflict stood. The
next PR had to be pushed past the hook with `--no-verify` to break it.

**The rule.** `main`'s build is the runs a push to `main` triggers. A Dependabot job (event
`dynamic`), a manual `workflow_dispatch` and a scheduled scan record the same sha and are not it.
The filter is the API's `--event push`, not the `--jq`: filtered client-side, `--limit 30` counts
the Dependabot jobs too, and a burst of them after a merge pushes the head's own runs out of the
window, which reads as "not built yet" for ever. A head with only non-push runs still waits — even
a manual dispatch that recovers a push event GitHub dropped, which is the rule's cost: that head
waits until a human installs a temporary `main-green` override (`PROTOCOL.md` says how).

**The watcher follows the same rule (2026-09-13).** `watch_ci.py` counted every run on the sha, so
a lock holder confirming `main` after a merge read the same failed Dependabot job as RED. It now
asks GitHub's compare endpoint whether the commit is on `main` — for `--branch main`, `--sha` and
local HEAD alike, since a local `origin/main` can be stale — and judges a commit on `main` by its
push runs only, the filter again the API's. `--pr` keeps every run on the head: Dependabot and the
scheduler run on the default branch alone, so filtering a pull request would only drop a dispatch
someone ran against its branch. A comparison that fails, or answers in neither allowlist, is no
verdict. `test_watch_ci.py` drives `main` through a fake GitHub that filters before it pages and
runs the real `--jq`, and plants each check that decides which runs count into a copy of the
script. The `gh run list` reads of `main` that the session start and the live checks instruct
gained `--event push` for the same reason.

**What generalises.** A gate that blocks until X is a deadlock when X can only be reached through
the gate, so a verdict the gate itself makes permanent has to be ruled out, not waited out. And a
check keyed on a commit sha inherits every bot that records a run against that sha — the
population (the fence above) is defined by the trigger, never by the sha. `pre_push_test.py`
carries the incident as a case beside one where a failed push run still reads RED, drives the
check through a fake `gh` that runs the queue's real `--jq`, and plants each of its checks.


## A scanner's configuration is its command line, and what it discovers is refused (2026-09-14)

**What happened.** A reviewer reported, and a throwaway `checkov==3.3.9` reproduced, that Checkov
reads `.checkov.yaml` and `.checkov.yml` from the directory named by `-d`, from the working
directory and from `$HOME`, even when `-f` names one file, and reads the environment variables

flag is on the command line. On a plan holding one `"Action": "*"` policy, the rendered-plan scan

sits outside the three list files the gates name, so no reviewer reads it as a change to a gate.

**The `.tf` and Dockerfile gates failed closed, by accident.** Their numerator hard-errors when an
enforced ID is evaluated against nothing, which is what a `skip-check` of one produces, and the
message then blames a typo or a scanner rename. A `baseline` set in the file fails closed by
another road. One covering every failure leaves Checkov printing only its summary, which the scan
step's JSON check refuses; one leaving a failure standing drops `passed_checks` to zero. The keys

**No option turns discovery off.** `--config-file` is parsed BESIDE the discovered files: the
planted skip survived an explicit config that set only `framework`, and one that set

reading a config from the working directory.

**The rule.** A scan's configuration is its command line and the list files its gate names.

stale accept line. Every Checkov scan runs through `.github/scripts/checkov-scan.sh`, which asks
Checkov, with the same arguments and `--show-config`, what configuration it would use, and refuses
any section of that report other than the command line and the defaults. It is a whitelist, so a
section a later version names differently is refused too, and asking the scanner rather than
listing the places it looks covers a discovery location that a version bump adds. The section
names are Checkov's own and pinned with it. Which sources get recorded is ConfigArgParse's, and
Checkov does not pin that, so a release that stopped recording one is the silent case the corpus
below exists for. A refusal writes
nothing to stdout, so each scan step's JSON check fails. `checkov-plan-iam.sh` now also refuses a
file that holds no Checkov result: plain `jq` reads an empty file as success, and it would
otherwise have narrowed a refused scan to a clean zero.

`GITLEAKS_CONFIG_TOML` did the same. Each exited the way a scan with that many findings does. A
fifth route is git's, not gitleaks's, and the first review found it
by planting: gitleaks reads the history through `git log -p`, which prints "Binary files differ"
instead of the content of any path whose `diff` attribute is unset. A committed `.gitattributes`

**Their wrappers ask the tool that decides.** `semgrep-scan.sh` adds `--verbose`, which makes the
report list every target Semgrep skipped and why, and refuses a skip whose reason names an ignore
file. It matches on the word, so a reason renamed to another spelling that still says "ignore" is
refused as well; a rename that dropped the word would stop the corpus's plants being refused, which
fails the job there. Semgrep cannot report the
variables it reads, so every `SEMGREP_*` name is refused except the workflow's own
`SEMGREP_VERSION`. The pinned release holds no string by that name, and it is removed from
Semgrep's environment anyway, since a search of strings cannot see a name built at run time.
`gitleaks-scan.sh` asks two tools. Git is asked, with `git check-attr`, which `diff` attribute it
gives every path in the history, so every attribute source git reads is covered, a nested
`.gitattributes` and `.git/info/attributes` included, and a path it reports unset is refused. That
includes a file that is binary anyway, such as a `*.png binary` line, because telling the two apart
would mean reading every version of the path; the refusal says to write `-text -merge` where that
is what the line is for. The count of answers against the paths asked is that check's positive
control, since a loop over a misread answer finds nothing to refuse. The wrapper supplies `git` and
`.` itself and runs only from the repository's top level, so the repository git is asked about is
the one gitleaks scans, and `git check-attr`, which reads a path relative to where it runs, reads
the history's paths as the paths they are. Then gitleaks is asked, with the same
flags, at debug level. There it names its configuration's source and each ignore file it loads,
before the line saying which `git log` it runs. The wrapper refuses any line in that stretch it
does not know, and a log that never names the default configuration. The ask reads no commit
(`--log-opts=--max-count=0`): at debug level gitleaks prints decoded fragments of what it scans,
which `--redact` does not cover, so the real scan runs at its own level. Both wrappers own their
report path and delete it first, so a refused scan leaves nothing to count, and the Semgrep one
deletes it again on every exit but a scan that completed and was not refused. Its first draft
printed a refusal's list through `head`, and more skips than a pipe holds killed the script with
SIGPIPE before the report went. That closed a fail-open already in the workflow, where both
summary steps read a missing report as 0. They now read it as no count.

**Semgrep's built-in list is why the repository keeps an empty `.semgrepignore`.** With no root
file, Semgrep applies a default list under the same skip reason a pattern gets, and the list skips
every `test/` directory. At 77ae380a it was skipping all 15 files in `apps/portal/src/test/` while
the workflow's comment said test files are scanned. The file switches the list off, so any such
skip is a pattern somebody wrote. Scanning those files added no finding. `test_security_gates.py`
asserts that the file exists and holds no pattern, since a pattern that matches nothing yet reads
as a suppression until the day it matches.

**What proves them.** `semgrep-scan-test.sh` and `gitleaks-scan-test.sh` run in the scan job,
ahead of each scanner's scans, against the release that job installed. Each case starts from a
stale report that reads as clean. Semgrep's corpus plants a root pattern, a nested file, the root
file's absence, `SEMGREP_BASELINE_COMMIT` and five thousand ignored targets, and its clean case
asserts both fixture findings, one of them under `test/`. The gitleaks corpus plants each of its
four configuration sources and asserts that the refusal quotes gitleaks's own line about it,
because the refusal message names every source anyway. It plants a `-diff` or `binary` attribute
from a root `.gitattributes`, a nested one and `.git/info/attributes`, one naming a path only the
history still holds, and one with the scan started below the top level, and asserts the refusal
names the hidden path or the reason. Its clean cases, one with a `.gitattributes` naming only a
diff driver, assert both credentials by rule ID, that the real scan printed no debug line, and that
the wrapper left nothing in a temporary directory of its own. That last check first measured
nothing on a Mac, where `mktemp -d` without a template ignores `TMPDIR`; the wrapper now names one.
Stubs cover each log, report or attribute answer the installed release does not give. Every
refusal in the two wrappers, and every line that deletes a report or a temporary directory, was
planted once: twenty-two mutations, each reddening its own case, between green baseline runs. The
guards that stop on a missing argument or scanner were not, since no scan runs past them. Ten more
mutations went into the wiring, which now reads every
workflow for all three scanners through one table and runs each summary and gate step the way the
runner does: a refused scan, and a gate no step counted for, each fail for their reason, and a
clean report passes. One plant survived and removed code instead of earning a case: stripping
colour codes from gitleaks's log, which dropping each line's time already did.

**Not closed by this.** An inline suppression is still a route in Semgrep and gitleaks, where no
numerator reads what the scanner skipped. A `# nosemgrep` comment took a Semgrep finding off with no
trace in the report (2 findings became 1), and `--disable-nosem` brings it back. A `gitleaks:allow`
comment took a gitleaks finding off (1 became 0), and `--ignore-gitleaks-allow` brings it back.
This change sets neither flag. The environment variables Checkov reads directly rather than through
a flag are another route: `--show-config` cannot report them, and a review measured
`CKV_IGNORED_DIRECTORIES` taking the finding of a resource in a subdirectory off a `-d` scan while
the wrapper exited 0. And code the pull request controls runs in both scanning jobs before Checkov
does: `npm ci` runs install scripts in the security scan job, and the plan job runs
`lambdas/fleet.py` and `lambda_plan_guard.py`. A step can write `$GITHUB_ENV` for every later step,
which is how a flagless variable above would arrive without a workflow edit. The review that found
this measured an install script doing so. A `SEMGREP_*` variable arriving that way is refused,
because the Semgrep wrapper reads the environment itself, and a `GITLEAKS_*` one because gitleaks
reports it. Git's own settings reach gitleaks as well: the attribute check covers every source of
attributes, but a setting that changes what `git log -p` prints by other means, such as a diff
driver's `textconv`, lives in git configuration, which only the workflow or code the job runs can
set. The same review measured a fake `checkov` placed earlier on `PATH` that stripped one module's
failures from a `-d` scan while this corpus still passed. That `$GITHUB_PATH` places it there for a
later step is inferred. No wrapper can see either, and none claims to. Each closes a file added in
good faith, not code written to defeat the gate, which a pull request that can edit the workflow
could do more simply. Nor is content closed: a file git detects as binary by itself, one with a
NUL byte near its start, is not scanned (measured, 1 finding became 0), and Semgrep passes a file
over its 1 MB default without a finding.
