---
type: Decision
title: "The SPA deploy decides from what is running, not from a path filter — and the Lambda image deliberately does not"
description: "`deploy-spa-image.yml` decides from live state against the deployed commit, re-points unless the PRIMARY deployment settled, and never skips on a dispatch. Do not add a `paths:` filter, and leave the Lambda image building on every push: downstream workflows name `github.sha` as its tag."
---

**The running image is no longer `main`'s tip; it is the last commit that changed an input to the image.** `deploy-spa-image.yml` still fires on every push — there is no `paths:` filter — but a scope step now decides two things separately: whether this commit can change the **image**, and whether the **service** needs pointing at anything. Replayed over the 40 merges before the change, running both path tests exactly as the step does: 15 would have built, 4 would have waited for their apply without building, and 21 would have done neither. Each of those 21 was previously a full rebuild and a rolling replacement of the production tasks for a merge that changed nothing the container serves.

**A `paths:` filter was rejected for one reason, and it is sufficient on its own.** It cannot see the two things that make a deploy necessary with **no image change at all**: a task-definition revision Terraform registered on its own — the service carries `ignore_changes = [task_definition]` precisely so nothing but this workflow points at one — and a previous run that failed. A comparison against live state sees both, because its baseline is **read back from the service** rather than assumed.

**A revision the service was POINTED at is not a deployment that LANDED, and that distinction is the whole safety of the scheme.** `describe-services` answers with the task definition the service was last pointed at; the circuit breaker runs with `rollback = false` — deliberately, so a bad image fails the workflow — so a rollout that failed leaves `PRIMARY` sitting on the revision that failed and reports it as the service's own. Diffing against that reading is how a failed deploy becomes **permanent**: the re-run finds no change, and every later merge agrees, green, over the bundle from before it. So the skip path re-reads the PRIMARY deployment's `rolloutState` and its running-versus-desired counts and re-points rather than skipping unless the deployment actually settled. That check is also the **per-merge health assertion**: `Assert the service settled` cannot run on a skipped deploy, and without it a run that checked nothing would look exactly like a run that checked everything.

**The baseline is the deployed commit, never `HEAD~1`.** A run that skips and a run that fails both leave the next one comparing against what is genuinely still running, so a missed deploy heals on the next merge instead of compounding. Every unreadable answer fails in the **expensive** direction — no service, the placeholder image, a tag that is not a commit sha, a commit the clone cannot reach — because a cheap green that deployed nothing is indistinguishable from a real one. Two smaller shapes are load-bearing for the same reason: a dispatch **never** skips, since the reason to reach for the recovery lever is always something this step's own reasoning cannot see; and an image tag already in the registry means already built, because the repository is IMMUTABLE and a rebuild would fail at the push and nowhere sooner.

**The image scope list IS `spa-image.yml`'s `paths:`, and the sharing is the point.** That gate already skips *proving* the image when none of those paths changed, so the repository had already committed to that set being the image's inputs; reusing it adds no new assumption. What changes is the price of the list being wrong — a miss on the pull-request side left an image unproven and `main` built it anyway, while a miss here leaves production serving the previous bundle behind a green deploy. `lambdas/test_ci_scope.py` asserts the two select identically over a corpus, and running that comparison is what surfaced `packages/**` missing from the gate: an empty workspace directory is exactly the entry a list is easiest to be wrong about, and the first package to land in it would have changed the bundle with both lists looking away. The task-definition list is separate and much smaller — `infra/main.tf` and `infra/modules/spa/` — and it decides **when the family may be read, not what to do**. `Deploy Infrastructure` fires on the same push with no ordering between the two, and the SPA run reaches the family first: its first read comes seconds in, while the apply starts only after the Lambda image lands. So a push touching either path waits for that push's own `Deploy Infrastructure` run to finish — asked of GitHub by commit, since a revision's registration time cannot say which apply produced it — and then decides from live state like any other push: the newest-revision comparison points the service at whatever the apply registered, and a push whose apply registered nothing does nothing. The list used to **re-point without waiting**, and that lost the race every time it was measured: it rolled the tasks onto a clone of the revision the apply was about to supersede, and the register step, which counts `CONFIG_` keys and compares no value, passed a changed value green on the old one. A wait that never finishes refuses the run rather than reading past it; an apply that finishes red is warned about rather than failing the wait, though the register step's key count still refuses a revision missing a key. GitHub cancels a PENDING run when a newer one queues in the same concurrency group, in either workflow, and a change whose run was cancelled lands a push late, the same bound as a push of several commits. GitHub's `queue: max` would keep every pending run, but GitHub does not guarantee their order, and an SPA run that started after a newer one had changed the image would build the older bundle over it. Widening the list to `infra/` would now hold the SPA run on every infrastructure merge rather than deploy on it, for values that outside these two paths move only through a module output or a variable default.

**The Lambda image was deliberately left alone, and the asymmetry is worth knowing before someone "finishes the job".** Two downstream workflows name `github.sha` as the Lambda image tag and both fire on trigger sets **wider** than that image's own inputs: `deploy-infra.yml` polls ECR for `<sha>` for ten minutes and then hard-errors, and `deploy-lambdas.yml` fires on `infra/modules/**` while `point-lambda.sh` waits per function. With 19 of those 40 merges touching `infra/` and 18 touching `infra/modules/`, filtering that build converts a routine infrastructure merge into a red `main`. The saving it would buy is about a minute on the 10 merges in 40 that touch no Lambda input.

**There is a way to have both, it was verified, and it is still not worth it.** ECR with `image_tag_mutability = "IMMUTABLE"` **accepts** `put-image` adding a *new* tag to a manifest it already holds — confirmed against a throwaway repository, with the positive control that the same repository refuses a *different* manifest under an existing tag ("cannot be overwritten because the tag is immutable") and returns `ImageAlreadyExistsException` for the same manifest under its own tag. So a content-addressed build could alias `<sha>` onto an image it did not rebuild and keep every downstream consumer naming the commit. The reason not to: the alias makes an image tagged `<sha>` carry a **different** sha in `BUILD_VERSION`, which `lambda-image-matrix.sh` asserts against directly and which every log record correlates by. Buying a minute on 10 merges in 40 with a fleet-wide change to what the deploy stamp means is the wrong trade — but the capability is real, so the next person weighing it does not need to run the experiment again.
