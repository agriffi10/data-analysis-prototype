---
type: Decision
title: "Plans queue apart from applies, and meet at the state lock"
description: "`deploy-infra.yml` queues each pull request's runs in a concurrency group keyed by its ref, and a push and a dispatch, the two events that apply, in `deploy-infra`. **A plan is still never computed beside an apply, because `tofu plan` takes the state lock, so both commands carry `-lock-timeout`.** Do not put plans back in the apply group: by default GitHub keeps one pending run per group and cancels it for any newer run, so a pull request evicted a pending apply and nothing re-ran it, and `queue: max` is no cure, since GitHub does not guarantee its order and an older apply could run after a newer one. Group names are shared by every workflow in the repository, so no other workflow's group may match one of these. Do not drop either timeout: the default 0s fails whichever command reaches the lock second, which is a lost apply when that is the apply, and nothing goes red until a plan and an apply overlap. Do not rename `deploy-infra`, which lets an apply queued under the old name run beside one under the new, and do not turn on `cancel-in-progress`, since a cancelled plan can leave the lock held. `lambdas/test_config_workflows.py` holds all of it."
---

**The workflow had one concurrency group for every event, and GitHub's queue made that a hazard to applies.** The group exists so two `tofu apply`s never run against one state. But GitHub keeps one pending run per group and cancels it when a newer run queues, whatever that run's event, so a pull request opened or synchronised while a push's apply was pending cancelled the apply. Nothing re-ran it: the change waited for the next push that fired an apply, or for someone to dispatch one. None of the 100 push runs on `main` up to `65d60b36` ended `cancelled`, so it was a hazard rather than an outage, and the cure costs little.

**So the key depends on the event.** A pull request's runs queue in `deploy-infra-plan-<ref>`, one group per pull request, where a newer push to the same pull request replaces only that pull request's own pending plan. A push and a dispatch queue in `deploy-infra`, so applies still never overlap and a dispatch still behaves as the recovery lever it is. The apply group keeps its old name on purpose: renamed, an apply queued under the old name would run beside the first apply under the new one, and the change that renamed it fires an apply of its own. GitHub shares group names across every workflow in the repository and compares them without case, so a group another workflow uses, CI's `ci-<ref>` with `cancel-in-progress` on among them, could cancel a plan holding the state lock or evict a pending apply; the tests evaluate every workflow's group for a sample of refs and refuse a match.

**Plans must still never be computed beside an apply, and the state lock now does that job instead of the group.** The plan job runs `tofu plan` without `-lock=false`, so it takes the state lock, and the S3 backend's lock is the same one an apply takes. Measured on the local backend with OpenTofu 1.12.1, rather than CI's S3 backend and `~1.8`: a plan started while an apply held the lock failed at once with `Error acquiring the state lock`, and the same plan with `-lock-timeout` waited for the apply and succeeded. Separating the groups without a timeout would therefore have traded a rare lost apply for a likelier one, an apply starting during any pull request's plan. Both commands now wait, and the tests refuse a plan or apply in any workflow step whose lock is off or whose last timeout is under a minute, about how long a plan holds the lock. They read each command the way the shell and `tofu` do: continuations joined, quotes and comments removed, `--flag` read as `-flag`, a timeout taken from `=value` or the next word, the last of a repeated flag kept. **They read a small language and refuse everything outside it**, because shell has more spellings than any check can read: three review rounds each found one that an earlier version passed. So a lock flag must be written literally on the command; a variable may carry other flags only when the step assigns it literal values naming no lock flag; a plan or apply inside `$(...)`, backticks or another shell is refused unread; and `TF_CLI_ARGS` may be set only in an `env` block, naming no lock flag and no value from elsewhere. The same probe showed `tofu show -json` of a saved plan and `tofu output` running during an apply without waiting, so neither takes the lock, and the plan job's scan and the apply job's branding step need no timeout.

**The two timeouts are sized from the jobs they run in.** Over the 15 most recent successful pull-request and push runs before `65d60b36`, the plan step took 48 to 61 seconds and started about half a minute into a job of three to four, and the apply step took 47 to 274 seconds (`gh api 'repos/{owner}/{repo}/actions/workflows/deploy-infra.yml/runs?event=<event>&status=success&per_page=15'`, then each run's jobs). The plan waits fifteen minutes: past every apply in that sample, and still inside its job's thirty with the scans after it. A longer apply, like the teardown the apply job's sixty minutes were raised for, fails a plan red; a re-run clears it, and no apply is lost. The apply waits ten: a plan holds the lock for about a minute, so ten covers a run of them, and a lock nobody released still fails well inside the job's sixty. A wait now holds a runner, where a run queued behind the group waited for free, and an apply's wait counts against the fifteen minutes `deploy-spa-image.yml` waits for unfinished applies. That is no worse than before: an apply used to wait behind a whole plan job of three to four minutes, and now waits for a plan step of about one, though the full ten would not fit.

**Rejected:** `-lock=false` on the plan. It needs no timeouts and never blocks an apply, but the plan a pull request is judged on, which feeds the Checkov IAM gate, the plan guards and the plan comment, would then be computed while an apply was changing the infrastructure it refreshes against.

**Rejected:** one group for every event with `queue: max`, which keeps up to 100 pending runs instead of one, so a plan would never evict an apply and nothing would contend for the lock. GitHub's documentation for it says runs start first in, first out by when each began waiting, and then that "ordering is not guaranteed". For applies the order is the point: a pending apply of an older commit starting after a newer one would put the older configuration back. It would also hold every apply behind every queued plan job, and run every superseded plan of a pull request.
